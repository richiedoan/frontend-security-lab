# Day 5 realm seed

`realms/lab-realm.json` is a hand-written, sanitized import for local development
with the pinned Keycloak image in `../compose.yaml`. It contains no passwords,
password hashes, client secrets, signing keys, or real user data. Runtime keys
are generated by Keycloak and stored in the local database.

| Setting | Value |
| --- | --- |
| Realm / issuer | `lab` / `http://localhost:8080/realms/lab` |
| Client | `security-web`, public OpenID Connect client (client authentication off) |
| Flow | Authorization Code enabled; implicit, password/direct grants, service accounts, device flow and CIBA disabled |
| PKCE | Required method `S256` |
| Redirect URI | `http://localhost:3000/auth/callback` |
| Web origin | `http://localhost:3000` |
| API audience | `security-api`, included in access tokens only |
| Default API scope | `documents:read` |
| Realm roles | `user`, `admin` |
| Users | `alice` and `bob`: `user`; `admin`: `user` and `admin` |

The separate public client `security-second-app` uses only
`http://localhost:3001/second-app/callback` and web origin
`http://localhost:3001`, with the same code-flow/PKCE restrictions. It has only
the `profile` default scope and no API audience mapper or role scope mapping.
See the [two-app SSO walkthrough](../../docs/labs/keycloak-sso.md).

There are no wildcard redirects or alternative hosts. Port 3001 is registered
only for the second client's exact callback, never for `security-web`. The
callback URI is implemented by the web app's [Day 5 login](../../docs/labs/keycloak-oidc.md).
The `admin` realm role is an application lab role,
not a Keycloak administration role. Role scope is limited to the two lab roles;
the standard `roles` client scope exposes assigned roles in `realm_access.roles`.

The users have stable seed UUIDs ending in `000001` (Alice), `000002` (Bob), and
`000003` (Admin). The API's separate OIDC document fixtures use these subject IDs
for ownership, never editable usernames. See the
[resource server contract](../../apps/api/src/oidc/README.md).

## Import

From `infra/`, after the initial `.env` setup described in the parent README:

```sh
docker compose up -d --wait --wait-timeout 180 postgres keycloak
docker compose logs --tail=100 keycloak
```

Compose mounts the seed read-only and uses `start-dev --import-realm`. Keycloak
imports a missing realm and **skips an existing realm**, preserving local changes
and passwords. This also applies if `lab` already existed before adding this seed.

To explicitly reapply the checked-in seed, the following replaces the local
`lab` realm, including users and passwords. Stop Keycloak before doing so:

```sh
docker compose stop keycloak
docker compose up -d --wait postgres
docker compose run --rm --no-deps keycloak import --file /opt/keycloak/data/import/lab-realm.json --override=true
docker compose up -d --wait --wait-timeout 180 keycloak
```

Check the import command succeeds before restarting. Reapplying the seed or
resetting the database requires repeating password setup below. Do not replace
the tracked seed with a raw export; exports may contain credentials and keys.
Use the ignored `infra/realm-data/` directory for local exports.

## One-time manual admin action: local passwords

The imported accounts cannot sign in until an administrator sets passwords.
`UPDATE_PASSWORD` alone does not let an account without credentials log in.

1. Open <http://localhost:8080/admin/> and use the bootstrap administrator from
   your local `.env` (separate from the `lab` realm's `admin` user).
2. Select realm **lab**, then **Users**. For each account you need (`alice`,
   `bob`, `admin`), open **Credentials → Set password**.
3. Generate a unique disposable password locally, keep **Temporary** enabled,
   and save. Do not use a real account's password or commit the generated value.
4. On first successful browser login, set a new unique local password when
   prompted at <http://localhost:3000/labs/oidc>. You can also use
   <http://localhost:8080/realms/lab/account/> for this step; that uses Keycloak's
   built-in account client, not `security-web`.

No manual client, role, or role-assignment changes are needed.

## Offline validation

From `infra/`:

```sh
node keycloak/validate-realm.mjs
docker compose --env-file .env.example config --quiet
```

These check JSON and the lab's required configuration shape without starting
containers or applications. They are not a live Keycloak import or browser-flow
test. Once running, inspect **Clients → security-web** for Standard flow,
client authentication off, exact redirect/origin, and PKCE `S256`. Check
**Clients → security-second-app** against its separate values above as well.

References: [Keycloak import semantics](https://www.keycloak.org/server/importExport)
and [PKCE configuration attribute](https://www.keycloak.org/docs-api/26.6.4/javadocs/constant-values.html).
